# Анализ trustos: почему site0, а не site2

Прошивка: RMX3581_11.A.75 (Android 11), раздел `trustos_a` = 6 MiB, магия заголовка `0x42544844` ("DHTB"), `mImgSize = 0x1b8570`.

## Детект паттерна (эвристика dis_avb)

Паттерн ищет последовательность `MOV W0, Wn` непосредственно перед эпилогом функции
(цепочка `LDP`s + `RET`) внутри функций нужной формы. На образе обнаружено **две** точки:

```
detected mov at 0x5afbc (bl=5 cbz=1  start=0x5af10)
detected mov at 0x5cb74 (bl=5 cbz=11 start=0x5ca18)
```

| Точка | Адрес | Обнаружено в | Суть |
|---|---|---|---|
| **site0** | `0x5AFBC` | функция, вход `0x5AF0C` (STP-пролог `0x5AF10`), 1 CBZ | **внутренняя функция** проверки; возвращает `w20` |
| **site2** | `0x5CB74` | функция-**обёртка**, вход `0x5CA18`, 11 CBZ | вызывает внутреннюю функцию и возвращает её результат |

Обе инструкции — `mov w0, w20` (возврат результата из callee-сохраняемого регистра). Замена:
`0x52800000` = `mov w0, #0` → функция всегда «успешна».

## Дизассембл (capstone, ARM64, хвосты обеих функций)

### site0 — внутренняя функция (`0x5AF0C`) — патчим ЕЁ

```
0x5af7c: cbz   x0, #0x5b44c
0x5af80: adrp  x1, #0x87000
0x5af88: add   x1, x1, #0x118
0x5af8c: bl    #0x5d0f4            ; внутренний вызов (проверка)
0x5af90: mov   w22, w0
0x5af94: …bl   #0x5d27c
0x5afa4: cbnz  w0, #0x5afe0        ; ветка отказа
0x5afac: mov   w20, #6             ; код ошибки 6 → log @0x6c45c
0x5afb8: mov   sp, x29
0x5afbc: mov   w0, w20             <== ПАТЧ → mov w0, #0
0x5afc0: ldp   x19, x20, [sp, #0x10]
  …5× LDP…
          ret
```

### site2 — обёртка (`0x5CA18`) — патч НЕ работает

```
0x5cb48: bl    #0x5af0c            ; вызывает ВНУТРЕННЮЮ функцию (site0)
0x5cb50: mov   w20, w0             ; сохраняем результат
0x5cb54: cset  w0, ne
  …
0x5cb74: mov   w0, w20             <== site2 (штатная эвристика апстрима)
          …LDP…
          ret
```

## Эмпирический результат (проверено на устройстве)

| Конфигурация | Исход |
|---|---|
| trustos с патчем **site2** + патченный boot | ❌ **bootloop** (мигание заставки + вибрация) |
| trustos с патчем **site2** + **стоковый** boot | ✅ грузится (патч безвреден сам по себе) |
| trustos с патчем **site0** + патченный boot | ✅ **грузится, Magisk 30.7 активен** |

**Вывод:** цепочка загрузки вызывает внутреннюю функцию `0x5AF0C` **напрямую**, минуя обёртку
`0x5CA18`. Принудительный `0` в обёртке её не перехватывает → верификация boot остаётся
включённой → неподписанный boot отвергается → петля. Патч site0 действует на **оба** пути
(обёртка возвращает результат внутренней функции — где бы её ни вызвали, вернётся 0).

## Почему «готовые» dis_avb петляют

Апстрёмный C-код (`src_main_common.c`) при `mov_count == 2` делает `mov_count -= 1` и патчит
`pmov[1]` — то есть **site2**. Для этой модели (и, вероятно, всего семейства sc9863a/Realme) это
неверный выбор. Порт `tools/dis_avb_port.py` принимает явный индекс сайта:

```bash
python tools/dis_avb_port.py patch sml trustos 0   # site0 — правильно
python tools/dis_avb_port.py patch sml trustos 1   # site2 — штатная эвристика, НЕ работает
```

Само ядро патчера — байтово-точный порт `dis_avb()` + `bsp_cve_2img()` (включая логику
`size_t`-переполнения в выборе `mov_count`, маску `0xFF00FFFF` при вырезании STP/LDP и
проверку `u16 == 0x3E0`); `selftest` — `ALL PASS`.

## Справочные sha256 (прошивка A.75, свежие дампы)

> На других устройствах/сборках значения могут отличаться (особенно `sml`).

| Файл | sha256 (начало…) |
|---|---|
| `trustos` (оригинал) | `f791b3bb…a3ab` |
| `sml` (оригинал) | `e2bc1153…e82a5` |
| `boot_a_orig.img` (оригинал) | `30d2c2e7…2b7bc0a` |
| `tos-noavb-bsp-bypassed-site0` (патч site0) | `388a3e2a7acbbe15…e8a94b46` |

Патч меняет ровно **4 байта** в `trustos` (`0x5AFBC`: `2a 14 03 e0` → `00 00 80 52`).
